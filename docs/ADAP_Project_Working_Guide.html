1 · The big idea

What is ADAP?

ADAP is a demonstration web application. It combines activity records from four synthetic data files and shows them in one simple interface.

Daraz

Important: all included records are made-up test data. The project does not connect to real provider accounts or live devices.

2 · Architecture

How data moves through the app

The browser never reads the CSV files directly. The server loads, checks, and prepares the data before sending only the requested result to the screen.

BrowserSearch, profile, timeline, map, charts
›
Next.js APIChecks the request and calls the data layer
›
Provider adaptersRead each source in a common way
CSV filesStay inside the server-side data folder
›
Validation + indexesReject bad rows; index phone and user ID
›
Unified activitiesCommon fields for sorting and filtering

Why there are adapters

Each provider CSV has different field names. For example, one source may use an order time while another uses a request time. Each adapter translates its own rows into the same normalized activity shape.

Before normalization
  • Different timestamps
  • Different activity types
  • Different provider details
After normalization
  • One occurredAt time
  • One provider label
  • One searchable and sortable model
Result: timeline, analytics, map, and report code can work with one model instead of understanding four CSV formats.

3 · Request walkthrough

What happens when you search

1

Enter a phone number

The user enters an exact 11-digit number, such as 01000000001.

2

Validate the request

The API checks that the value has the correct format. Bad input gets a safe error.

3

Query all adapters

The server asks Foodpanda, Daraz, Pathao, and Uber adapters at the same time.

4

Use fast indexes

Each dataset already has lookups by phone and user ID, so matching rows can be found quickly.

5

Combine the records

Records are normalized, merged, and sorted by the real event time—not by the source update time.

6

Return only the result

The API sends a consistent JSON response. The page renders the profile or chosen view.

Partial failures do not break everything

The four provider requests use a partial-failure-tolerant pattern. If one provider fails, successful results from the others can still be shown, and the failed provider is reported in response metadata.

Search → API validation → 4 provider queries → normalize → sort → response → screen
Simple authentication: protected screens use a demonstration session cookie. This gate is useful for the demo, but it must be replaced with production-grade identity and authorization for real use.

What each part of the interface does

DashboardSearch by phone number and see provider health, user totals, and record totals.

Caching in simple words

The first request in a warm server process reads and validates the CSV files. ADAP keeps the prepared datasets in memory, so later requests can reuse them. In serverless hosting, each server instance has its own cache.

The simplest summary

ADAP reads four private synthetic CSV files, validates them, finds matching user records through adapters, converts them into one common activity format, and shows the results through secure-ish demo pages and APIs.

Before any real-world use

  • ✓ Replace the demo login with real identity, roles, and authorization.
  • ✓ Move browser-local cases, notes, and audit records to protected persistent storage.
  • ✓ Add encryption, access review, retention rules, monitoring, and formal data agreements.
  • ✓ Keep the safety boundary clear: the current application is a synthetic demonstration.
